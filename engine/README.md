# 自研引擎（玩法沉淀）

> 团队自研 crate 仓库：装**跨玩法可复用**的"主观玩法机制"（数值引擎、通用战斗原语、验证工具等）。
> **不是"自造引擎底座"**——引擎底座是 Bevy（ADR-0004 已退役手写渲染/ECS 路线），客观技术（物理/碰撞/粒子）走生态插件。
> 沉淀时机：**玩法机制第 2 次被另一个游戏用到，才从已留好的接缝处机械抽出**（见根 `AGENTS.md` / 知识库"免重复准则"）。
> 不为"看起来有引擎"而提前抽 code——首例 ADR-0010（showroom-viewer）即以"引擎 crate + 独立 bin"双消费方成立。

位于整体 monorepo 内，不单独建仓：

```
engine/<crate-name>/     # 例如 engine/<crate-name>/
```

## 现有 crate

- `showroom-viewer/` — 通用中性影棚资产查看器（ADR-0010）：影棚环境/清扫/资产目录/egui 列表/
  环绕相机全部通用；各游戏只注册自己的目录（warden 已接入），另带零接入的 `asset-viewer`
  bin（`cargo run -p showroom-viewer --bin asset-viewer -- <目录>` 扫看任意 GLB）。

## 放什么

- **主观玩法里、被 ≥2 个游戏复用的机制**：数值引擎 + 数据驱动/热调、通用战斗原语（伤害结算/冷却/弹体）、验证工具（headless 平衡读数/难度曲线）、通用骨架（如简单 FSM）等。
- **不放**：
  - 客观技术（物理/碰撞/粒子/渲染/ECS）→ 走 Bevy + 生态插件；
  - 具体玩法逻辑与数值 → 各游戏自己（schema 各藏）；
  - 单游戏特有、尚未被第 2 个消费方用到的 → 各游戏自己，等到第 2 次再用才抽。

## 沉淀时机

| 时机 | 做法 |
|------|------|
| 第 1 次用 | 写进当前游戏正常用；把**可装配接缝**留标准（SystemSet 阶段 / 插件边界 / 消息与组件契约）——即使暂只有一个游戏消费 |
| 第 2 次用 | 从已留好的接缝处**机械抽出**独立 crate，沉淀到 `engine/`（带版本号），本游戏通过 `path` 依赖引入 |
| 3 次以上 | crate 稳定后按需升版本，各游戏独立升级 |

**两层免重复全景**：客观技术 → 引用生态插件（不重复造别人的轮子）；主观玩法 → 沉淀成自己的 crate（不重复写自己的轮子）。详见团队知识库 `docs/topics/engine/bevy-plugin-and-code-reuse.md`。

## 游戏如何依赖引擎

- 开发期：游戏里用 `path = "../engine/<crate-name>"` 快速迭代。
- 稳定期：crate 打版本号后，游戏改用 git 依赖锁定版本（同仓库内提交即可，无需独立远程仓库）。
