# ADR-0002: 引擎边界——游戏驱动、不做通用引擎、能力卡为核心资产

## 背景

M1（窗口/清屏/三角形/移动/相机/MVP）完成后，团队提出质疑：**自研引擎的实用性可能不高**——市面上成熟引擎为无数场景做过打磨（如 delta time 的固定时间步、累积器、渲染插值、time scale），自研版本必然考虑不全面；且与 Unity/Godot 相比，自研引擎几乎不可能达到「通用商业引擎」的完成度。

同时团队明确了协作模式：AI 负责实现，人负责写规格（能力卡）与验收。这一定位直接影响「引擎要做成什么样」。

## 决策

1. **不做通用引擎**。引擎的唯一服务对象是团队自己的游戏，不为假想的外部用户设计任何功能。成功标准 = 「下一款游戏用它做，顺不顺手」，不与 Unity/Godot 比功能覆盖面。
2. **游戏驱动开发**。引擎能力只从真实游戏需求中提炼（demo 游戏驱动引擎），禁止为「将来可能用到」预付复杂度。若出现无游戏消费的引擎功能，视为引擎跑步机征兆，需立即叫停。
3. **能力卡库是核心资产**。能力卡描述 WHAT（接口/行为/验收），不绑定 HOW（具体 Rust 实现）。引擎可以重写、替换甚至放弃，能力卡与领域认知平移到任何技术栈。
4. **复杂度按需引入**。成熟引擎的通用性（固定时间步、渲染插值等）是为海量场景付的「通用性税」；本团队在真实撞上问题（如碰撞穿透）时再引入对应方案，且引入时必须先立 ADR 说明理由。
5. **AI-native 假设优先于引擎完成度**。本引擎同时是「能力卡 + AI = 小团队高倍速」工作流的试验田。用 M2 游戏尽早验证该假设，比打磨引擎更重要。

## 备选方案

- **对标通用引擎补全功能**：死路。通用性税会吞噬 3 人团队，且无外部用户可回血。
- **放弃自研，直接用 Godot/Unity 开发游戏**：出活最快，但放弃 AI-native 工作流验证与团队内功积累；且与既有 ADR-0001 冲突。否（但保留为逃生通道：能力卡可平移，见决策 3）。
- **用 Bevy 全量框架**：引擎大头由社区维护，但框架替我们做了太多决策，验证不了自己的架构能力。部分借鉴（bevy_ecs）已在 ADR-0001 记录。

## 影响

- 引擎与游戏的边界以「提炼」方式形成：先在 demo 游戏里实现，模式稳定后提炼进引擎层（M2 期间开始）。
- 所有「引擎要不要支持 X」的讨论，判定问题统一为：「当前游戏需要 X 吗？」
- 战略摇摆时可重读本 ADR 的「背景」一节：实用性质疑的答案不在引擎里，在游戏里。
- 本 ADR 状态为 proposed，团队 review 通过后改 accepted；被取代时更新状态。
