# ADR-0014: 开发流程简化——能力卡工作流退役，规格-测试-小步提交

## 背景

能力卡（立卡 → 实现 → 验收 → 回归 → 一卡一提交）在 warden/wave-survival 阶段解决了两个问题：给 AI 写数字化需求规格、让验收可执行。它当时是必要的，因为**没有更重的规格载体**。

warbase 立项后载体已经升级：架构/实现/测试三份设计文档比卡详尽得多（接口、类型、调度、阶段划分全有），测试用例全集（UT/G-LP/W/BAL 系）本身就是验收句的可执行形态，根 workspace 让 `cargo test --workspace` 成为一击回归门禁。卡剩下的只有登记记账功能——立卡记录、卡模板、状态登记册，纯粹的重复劳动（youxia 2026-10-08 拍板：「没什么必要了，有点多余了」）。

## 决策

1. **能力卡工作流全面退役**：不再立卡、不再维护 `capability-cards.md`、不再要求卡模板/卡 ID 仪式。既有卡文件**停更存档**（warden/wave-survival 的卡文件是开发日志，保留不动）。
2. **接替流程（规格-测试-小步提交）**：
   - **规格先行**：行为与验收标准写进设计文档（GDD / requirements / 设计稿），验收标准必须数字化、可执行——写不出来 = 没理解清楚，不开工（继承卡的灵魂）；
   - **红绿实现**：先写测试（红）再实现（绿）；新机制 = 新组件 + 新系统，老系统零改动；
   - **一击回归**：`cargo test --workspace` 全绿是提交门禁；
   - **一增量一提交**：Conventional Commits，英文，可回滚（继承「一卡一提交」的小步纪律，只是不再需要「卡」这个文档前置）。
3. **进度追踪**：各项目 `docs/roadmap.md` 一张平面状态表（增量 × 内容 × 状态），无仪式。既有 BX/WX/TS/MA… 编号作为**增量名**继续使用（设计文档与提交历史引用它们），只是不再是「卡」。
4. **模板同步**：`templates/bevy-game/` 的 AGENTS/README/GDD 改为新流程，`docs/capability-cards.md` 移除、换 `docs/roadmap.md` 模板。
5. ADR-0002 决策 3（能力卡库是核心资产）相应修订：核心资产现为**设计文档 + 测试 + 沉淀代码（engine/ crate）**；「描述 WHAT、不绑定 HOW、可平移」的精神继续成立，载体从卡换成了文档与测试。

## 备选方案

1. **保留卡、只减模板字段**：仍是双层记账（规格在文档、状态在卡），没有解决「多余」本身。否。
2. **仅对 engine/ 侧退役、游戏侧保留**：两套流程并存增加认知成本，且游戏侧同样已有 requirements/GDD。否。
3. **全部退回「口头需求 + 直接写码」**：会丢掉小步提交与验收先行这两条被 warden 验证过的纪律。否——退役的是形式，纪律进流程。

## 影响 / 后果

- 少一层文档维护；规格单一事实源 = 设计文档，验收单一事实源 = 测试。
- 风险与对冲：小步纪律弱化 → 由「红绿 + 一增量一提交 + workspace 一击回归」硬性承担；人类可见的进度视图 → roadmap.md 平面表。
- 历史 ADR/笔记（0002、capability-card-workflow-deep-dive、ai-feature-pipeline-sop 等）不改写，本 ADR 记录流程变更即可。
