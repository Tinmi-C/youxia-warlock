# ADR-0007：动画状态机采用表驱动形态（面向动画规模增长）

> 本 ADR 与 ADR-0006 是一对：ADR-0006 否决"换引擎用 bevy_animation_graph"，
> 本 ADR 决定"动画状态机采用什么形态"。背景链接：Wave Survival 确认动画会
> 持续增多（20+ 状态，多武器攻击/技能/敌人多形态/死亡受击胜利等）。
> **2026-09-02 用户确认方向 + 阶段划分：阶段 1 = 表驱动状态机 + 轻量 egui 监控面板，
> 阶段 2 = 可视化编辑器（后置）。故本 ADR → accepted。**

## 背景

- `games/wave-survival/src/plugins/presentation.rs` 的 `sync_walk_playback`
  是一个 ~240 行手写状态机：`HeroClip` 枚举 + if/else 分支 + one-shot 窗口
  计时 + 战斗边沿检测 + 播放速率刷新，含 7 状态（hero 5 + 怪物 2 共享）。
- ADR-0006 已实证 bevy_animation_graph 的 StateMachine 转场只认事件、不支持
  输入条件比较，故"状态=图节点、转场=条件边"的承诺落空，**换引擎不可行**。
- 用户确认动画规模会显著增长（预计 20+ 状态）。届时现有手写状态机每加一个
  状态都要碰 `sync_walk_playback`，函数只会越来越大、交叉分支越多，最终失控。
- 项目边界（根 AGENTS.md + 本项目 AGENTS.md）：客观技术能力优先用生态插件、
  不自写引擎件；主观玩法逻辑（手感/节奏）自研并在能力卡沉淀。

## 问题拆解

问题**不在播放引擎**：Bevy 内置 `AnimationTransitions`/`AnimationPlayer` 已能
播放任意 clip、平滑转场，这一层完全够用。问题在于**"哪些状态、何时切换"被
硬编码在 `sync_walk_playback` 的 match/if-else 里**，导致状态增多时控制流爆炸。

因此：**不换动画播放引擎，只把"状态机拓扑"从代码搬进数据**。

## 决策

**采用表驱动动画状态机。** 把状态机定义成一张配置表 `AnimStateTable`
（`Vec<AnimState>`），一个通用调度系统 `drive_anim_states` 读表驱动播放。

- 每个状态 = 一条 `AnimState` 表数据（clip/循环/速率/转场条件/回退/blend）。
- 转场条件用 `Transition` 枚举表达（速度阈值/moving/战斗边沿等，见卡 33）。
- 加状态 = 加一条表数据；`drive_anim_states` 的控制流**一次写好、永不改**，
  与状态数量无关。
- **关键边界**：状态机**拓扑**数据化（主观玩法自研），**播放**仍走 Bevy 内置
  `AnimationTransitions`（客观能力用现成）——不违背"不手写引擎件"。

### 备选方案
| 方案 | 评价 | 结论 |
|---|---|---|
| A. 拆纯函数（decide_hero_state + 配置表，行为不变） | 治乱不治本：状态多了仍是手写逻辑分支，只是整齐 | ❌ 不足（动画 20+ 时仍失控） |
| B. 按职责拆文件（model/animation/weapon/…） | 只解决"一文件 7 职责"，不解决"状态机增长" | ❌ 不足，可作附带整理 |
| C. bevy_animation_graph（图数据状态机） | 已证伪（转场只认事件，逻辑下不去） | ❌ 不选 |
| D. 自建通用状态机引擎 | 违背"不手写引擎件"，且动画规模不足以自建通用引擎 | ❌ 不选 |
| **E. 表驱动状态机（本决策）** | 拓扑数据化（加状态=加表数据），播放用现成引擎 | ✅ 选定 |

## 影响 / 后果

**好处**
- **治增长**：加状态=加一条表数据，控制流零改动。动画 7→20→50 均适用。
- **可测**：`derive_next_state(current, inputs)` 是纯函数，可直接单测。
- **数据化**：状态拓扑直观；配合现有 F1 egui 面板可显示当前状态/切换日志。
- **AI 高效**：改状态只改表，改不到控制流，命中率高、零风险。
- **合规**：播放走 Bevy 内置，不自建引擎。

**代价**
- **一次性架构成本**：定义表结构 + 写通用驱动系统 + 迁移现有 7 状态到表 +
  写测试，比"拆纯函数"大。
- **迁移风险**：现有 7 状态行为必须逐字保留，靠 59 回归 + 真机肉眼验收兜底。
- **取舍**：`Transition` 是条件枚举（非任意表达式），覆盖已知判断类型。若将来
  出现全新判断（如"血量百分比触发"），加一个 `Transition` 变体——不碰驱动
  系统主逻辑，比改巨型函数可控。
- 只解决"状态机拓扑扩展"，不解决动画资产/模型本身扩展（美术管线另议）。
