# ADR-0008: 游戏数值数据暂留代码内，不外部化到数据文件 / 数据库

## 背景

wave-survival 做了“数据驱动”的数值层：敌人/武器定义表（`games/wave-survival/src/components.rs` 的枚举方法）、`Balance` 资源（`resources.rs`）、波次公式（`systems/wave.rs`）、锚点目标带（`systems/balance_audit.rs` 的 const）。这里“数据驱动”指**把数值从逻辑里抽出来、集中成数据、系统只读**，但**并不等于“存进数据库或外部数据文件”**。需要明确：数值到底放代码里，还是外部化（配置表/数据库）。

## 决策

**当前把游戏数值（武器/敌人定义表、`Balance` 默认值、波次公式、锚点带）留在 Rust 源码中，不做外部化（不引入数据文件 / 数据库）。**

理由：
- “数据驱动”已达成：系统读数据、不硬编码；改数值 = 集中改一处。
- 团队 3 人都会写 Rust + 用 AI 编辑，改数值 = 改一行 + `cargo run --bin balance_report` 验证，没有“不重编译”痛点。
- 无专职策划、单机非服务型，无“外部改数 / 热更 / 遥测回调”需求。

运行时可调：`Balance` 资源经 F1 egui 面板**内存内热调**（重启丢失）；`balance_report` 的 what-if CLI 用**临时参数**预测，不落库、不改游戏。

## 备选方案

1. **外部化到数据文件（TOML/JSON/RON）**：改数不重编译。否——现在没人需要（无策划、程序员 + AI 改码即可），提前外置 = 过度设计 / 过早抽象。
2. **数据库 + schema / 热更 / 版本化**：服务型 / 遥测驱动平衡才需要。否——单机非服务，成本远超收益。

## 影响 / 后果

- 优：零基础设施；数值类型安全、单一事实来源；AI 可快速改 + 验证；符合“先留接缝、形状未定不抽象”。
- 代价：改数需重编译；数值不可由非程序改；不可热重载。

**迁移门槛（出现任一即重新考虑外部化）**：
1. 有 **不写代码的策划** 要调数；
2. 需要 **改数不重编译 / 热重载**；
3. 数值 **量大且互相派生/继承**（升级 / 装备 / 技能树），需要 schema 校验、分层、版本化；
4. **服务型 / 遥测驱动**平衡。

触发时：把通用数值引擎 + 数据加载/校验抽进 `engine/`，各游戏数值移到外部文件 / 数据库。
