# 游戏↔美术跨项目工作流（权威流程规格）

> 原则：**游戏项目是需求的唯一源头，美术项目（岩库 ArtVault）是资产的唯一权威仓**。两仓通过「需求看板 + 版本锁定清单 + 自动化工具」对接，全程不手拷文件、不口头传需求。本图覆盖从「游戏立项产生需求」到「资产升级/需求变更」的完整闭环。

## 全景图（五阶段 + 两个回环）

```
【A 需求提出】游戏侧              【B 制作】美术侧(岩库)         【C 验收同步】双向
 def/设计文档(需求源) ──art-needs 投影──> art-needs.json ──上板──> 需求看板(draft)
      │ 补充上下文(风格/规格/验收标准)         状态机: draft → locked → delivered
      └── 游戏侧确认 lock ──────────────────────────┘
                                                                    │
                              制作(岩库内部流程) <─── 领取 locked ───┘
                                                                    │
 游戏仓 art-assets.json(版本锁) <──art-sync 拉取── 岩库入库(版本化) <──┘
      │                                    │
      ├─ 自动取证(结构断言/转台/像素差)      ├─ 岩库侧入库校验
      ├─ 游戏侧接入(挂 def/换装面/动画机)    └─ 回流: 游戏再加工 save_asset 回岩库
      └─ 人工关卡 H-ART(看图拍板)
【D 升级回环】岩库新版 → 改清单版本号 → 重跑 art-sync → 回归
【E 变更回环】游戏改 def/需求 → 看板 changed → 美术重做 → 重新走 C
```

## A 需求提出（游戏侧，AI 全自动 + 人工定优先级）

| 步 | 动作 | 产物 | 责任 |
|---|------|------|------|
| A1 | 游戏增量产生内容（MapBundle def：单位/建筑/图标位；UI：设计系统的面板/图标清单；特效：fx 语义消息清单） | def 表 = **需求唯一源**（禁止两处维护） | 游戏 AI |
| A2 | `tools/art-needs` 扫描 def → 投影结构化需求（id/类型/几何规格/引用计数） | `<game>/art-needs.json` | 游戏 AI（工具自动） |
| A3 | 补充人工上下文：风格引用（UI=方案 A token 色板；3D=风格圣经条目）、用途与视角、**数字化验收标准**（如「转台 4 视角与基准像素差 0」） | 需求卡完整化 | 游戏 AI 起草 + 负责人审 |
| A4 | 推上岩库需求看板（demand），状态 `draft` | 看板条目 | 游戏 AI（CLI） |
| A5 | 需求定稿：确认无误 → `locked`（美术开工信号）；带优先级排序 | locked 需求 | **游戏侧人工拍板**（唯一人工点） |

## B 制作（美术项目内部，游戏侧不介入）

美术从看板领取 `locked` 需求 → 按岩库自身流程制作 → 产出入库岩库（版本化，附需求 id 回链）。游戏侧只在「需求描述不清」时被美术通过看板评论@回来。

## C 验收与同步（双向自动 + 一个人工关卡）

| 步 | 动作 | 门禁 | 责任 |
|---|------|------|------|
| C1 | 岩库入库校验（格式/命名/元数据） | 岩库侧 | 美术 AI |
| C2 | 游戏侧 `art-assets.json` 清单加/改条目锁版本 → `tools/art-sync` 拉取（**字节级校验**，不手拷） | 清单与资产文件一并提交游戏仓 | 游戏 AI |
| C3 | 自动取证验收（四手段按适用矩阵：结构断言 / 转台录屏 / 紧裁剪双帧 / 像素差——见视觉验收取证规范） | 断言红→绿 | 游戏 AI |
| C4 | 游戏侧接入：3D 挂 def+分件动画机；UI 走 token/贴图换装面（`art-mapping.json`）；特效按 fx 消息映射 | headless 测试**不依赖资产**（结构断言与视觉取证分离） | 游戏 AI |
| C5 | **H-ART 人工关卡**：看图拍板（自动截图包/转台图呈负责人） | 通过才算资产闭环 | **游戏侧人工** |
| C6 | 回流：游戏侧再加工（分件手术/材质调整）→ `save_asset` 回写岩库（同门入库不豁免规范） | 岩库版本+1，清单升级走 D | 游戏 AI |

## D 资产升级（岩库→游戏）

改 `art-assets.json` 版本号 → 重跑 art-sync → C3-C5 全门禁重走。游戏仓内任何时刻的资产状态**可复现**（清单锁定纪律）。

## E 需求变更（游戏→美术）

游戏改 def/设计 → art-needs 重新投影 diff → 看板对应需求转 `changed`（附变更说明）→ 美术按 changed 重做 → 重新走 C。**禁止绕过看板直接改资产**。

## 分工总则（AI/人）

- 游戏侧 AI：投影/上板/同步/取证/接入/回流全自动化（本仓已验证的多轮实践）。
- 游戏侧人：A5 需求定稿与优先级、C5 看图验收——**两个拍板点，其余零人工**。
- 美术侧：制作与入库按岩库自身流程（另一个项目自理）。

## 对接拓扑澄清（2026-10-29 补）

**唯一对接点原则**：游戏项目与美术项目之间的一切工件流（需求/资产/版本/状态）只经岩库，互不直连：
- 资产流：美术产出 → 岩库版本化入库 → 游戏侧 art-sync 拉取（美术永不直接给游戏仓塞文件）
- 需求流：游戏 def → art-needs 上板（岩库看板）→ 美术领 locked 单（美术看岩库的板，不看游戏仓）
- 变更/回流：同样经看板 changed 态 / save_asset 入岩库

**为什么星型而非点对点**：①游戏仓可复现性（清单锁版本，美术内部迭代不打扰游戏仓）；②需求状态机单一真相源；③岩库本就是多游戏共享中台——N 游戏 × M 美术的点对点会失控，星型天然支持跨游戏资产复用。

**两个人层例外（仍以岩库工件为载体）**：①需求澄清——美术对需求卡有疑问走看板评论@游戏侧，结论沉淀回需求卡；②风格共识——风格圣经与概念图应**存放于岩库**（或两边镜像、需求卡引用），保证两边看到同一份审美基准；游戏侧的方案 A brief 当前在游戏仓，美术解禁时应同步入岩库作为风格圣经初始版。
