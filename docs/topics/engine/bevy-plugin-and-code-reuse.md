# Bevy 开发约定：插件决策与代码沉淀

> 2026-08-25 团队讨论产出（youxia + AI）。ADR-0004 确定 Bevy 为默认底座后，固化两条「免重复开发」准则，避免三人各自重复造轮子。
> 准则已同步固化在 `templates/bevy-game/`（README「插件决策准则」+ AGENTS.md 硬性规则），本篇是团队级权威版本。

## 背景

- ADR-0004：Bevy 0.19.1 是团队所有未来游戏的默认引擎底座；自研 = AI 装配层（能力卡 + 验收闭环 + 观察通道）。
- Bevy 生态插件丰富，大部分通用技术能力有现成实现；团队的重复劳动来自两处：① 重复造通用轮子（别人的活）② 重复写自己的玩法模块（自己的活）。
- 两条准则分别消灭这两类重复。

## 准则一：插件决策（客观 vs 主观）

**判断标准：这个功能的「正确性」是客观的还是主观的？**

| 性质 | 定义 | 例子 | 做法 |
|------|------|------|------|
| **客观正确** | 技术难题，有标准答案（不穿墙=对，穿墙=错） | 物理/碰撞、角色控制器机制、粒子、缓动、网络、寻路、瓦片地图 | **引用生态插件**，不自己写 |
| **主观设计** | 玩法设计，无标准答案（手感/节奏/数值） | 移动手感、波次节奏、战斗数值、掉落表 | **自己写**，按能力卡沉淀 |

**混合拆解**：一个功能常是「客观机制 + 主观规则」的混合。例：移动 = 物理机制（重力/碰撞/爬坡，客观）→ 插件；手感规则（速度/跳跃/冲刺，主观）→ 自己调参。

**选型三原则**（引用插件前必查）：
1. **版本对齐** Bevy 0.19（[bevydepy.com](https://bevydepy.com/popular?bevy=0.19) 按版本过滤 / crates.io 看最近更新）
2. **维护活跃**（近半年有提交；Bevy 迭代快，停更插件很快失配）
3. **作者可信**（官方 / 知名组织优先，如 dimforge/rapier）

**决策图**：

```
这个功能的正确性是客观还是主观？
├─ 客观（技术难题）→ 找插件引用（版本对齐 + 维护度 + 可信度）
└─ 主观（玩法设计）→ 自己写，能力卡流程（立卡→实现→验收→回归→提交）
```

## 准则二：代码沉淀（先留可装配接缝，不提前造无人消费的通用层）

**判断标准：这个玩法模块被几个游戏需要？（提取时机）**

| 时机 | 做法 |
|---|---|
| 第 1 次 | 写进当前游戏正常用；但把**可装配接缝**留标准——SystemSet 阶段、插件边界、消息/组件契约（即使暂时只有一个游戏消费） |
| 第 2 次 | 从已留好的接缝处**机械抽出**独立 crate，沉淀到 `engine/`（团队自研 crate 仓库，独立 git 仓库 + 版本号） |
| 3 次以上 | crate 稳定后按需升版本，各游戏通过 path（本地）/ git（远端）依赖 |

**为什么是「先留接缝」而不是「第 2 次才抽」**：

反对的是「必须等第二款游戏才抽」——它不是改成「先建一个没人用的万能 RPG 引擎」，而是**第一款就把接缝标准化**（阶段、边界、契约）。这样第二款要复用时是**机械抽取**，而不是先猜接口再返工。

- game-driven **保留**：无游戏消费的空想模块仍不做；「引擎是长出来的」依然成立，改的只是抽公共层的**时间点**。
- 客观技术仍引用生态插件，不因「提前框架」去自研物理。

> 2026-08-31 复盘（§4.1）改此条：原文「第二次用到才抽」被否定——改的是时机，不是「先做万能引擎」。

**抽什么、不抽什么**：
- 抽：客观机制 + 稳定玩法模块（波次系统、战斗框架、通用 UI 组件）
- 不抽：一次性玩法、还在频繁改手感的模块

**两层免重复全景**：

```
第一层：客观技术 → 引用生态插件（别人的轮子，不重复造）
第二层：主观玩法 → 沉淀成自己的 crate（自己的轮子，不重复写）
```

## 与 AI 协作的结合

- `templates/bevy-game/AGENTS.md` 硬性规则「先找插件，不重复造」：AI 开发时同样先判断客观/主观，客观的先去生态找插件，禁止从零写。
- 能力卡流程保证「自己写的部分」可验收、可沉淀、可复用（卡 = 接口 / 行为 / 验收句）。
