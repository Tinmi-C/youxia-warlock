# 引擎定位与团队方向讨论纪要

> 汇总 2026-08-19 讨论：demo 先行策略、自研引擎的定位再思考（AI 装配层）、开发环境工作流。
> 总纲《AI 原生游戏引擎——设想总纲》是愿景蓝图，本文是落地方向讨论。
> 文中「✅ 已定」= 团队已拍板；「💡 建议/待确认」= 讨论结论，待团队 review。

## 1. 背景

- 3 名程序员，**无游戏开发经验**，边开发边学习。
- 总纲由一人起草，**未经团队细节讨论**（大家尚无经验，难以提出建设性意见）。
- ✅ **已定：demo 先行**——每人先开发一个游戏 demo，以此评估各自对游戏开发的理解程度，demo 也是后续讨论的共同语言。

## 2. 核心讨论：自研引擎的目的

**目的**：希望游戏开发中 ECS 能配合 AI，通过类似 skill 的方式做游戏开发，减少开发人员手工编写与联调。

**评估**：
- 方向合理，与行业趋势一致（AI 辅助/自主游戏开发）。
- 💡 修正一句：目标不是「不需要人」，而是「**人负责定方向、审核、处理 AI 搞不定的集成问题；重复性开发与联调交给 AI**」。

**ECS 为何对 AI 友好**：

| ECS 特性 | 为什么对 AI 友好 |
|----------|-----------------|
| 组件 = 纯数据结构 | 可序列化、可 schema 校验 → AI 擅长生成与配置 |
| 系统 = 对组件集合的函数 | 边界清晰、可独立验收 |
| World 可查询遍历 | 可观测、可测试 → AI 能验证世界状态 |
| 无继承纠缠 | 比 OOP 清晰，AI 生成不易踩隐形耦合 |

**关键洞察**：AI 自主装配需要的不只是 ECS，而是「**能力卡 + 标准总线 + 验收闭环 + 受控改动/可回滚 + 观察通道**」——即总纲中「标准总线（引擎的宪法）」那一层。**这才是真正值得自研的部分。**

## 3. 关键结论：重新定义「自研」

> 💡 **自研 ≠ 从零写渲染 + ECS；自研 = AI 装配层**（标准总线 + 能力卡体系 + 验收闭环）。
> 底料（渲染 / ECS）用现成开源，是专业常识；上层自己设计，才是「自研」的分量。

**三方案对比**：

| 方案 | 底料 | AI 装配层 | 评价 |
|------|------|-----------|------|
| A 全自研 | 手写 wgpu + 手写 ECS | 自研 | 学习价值最大，但离 AI 装配目标最远 |
| B 混合（💡倾向） | 现成（wgpu / bevy_ecs） | **自研（核心）** | 最快到达「AI 装配」，自研分量全在核心层 |
| C 现成引擎 + 现成 AI | 全现成 | 不造 | 最快出游戏，但无自主装配语义 |

**阶段安排**：
- ✅ M1/M2 继续手写 wgpu：学习价值不可替代（ADR-0001）。
- 💡 **M3 前认真评估 `bevy_ecs` 作底料**（省下几个月，力气花在 AI 装配层）。
- 💡 验收闭环与观察通道**不依赖底料选型，可立即开始设计**。
- 💡 **待立 ADR-0002**：AI 装配层 vs 自研引擎（本讨论结论正式化）。

## 4. 开发环境与工作流

- 现状：代码开发在 **Linux VM（无显示环境）**；运行/看效果在 **Mac**（本地电脑）。
- Remote-SSH 能编辑代码、跑终端，但**不能传输图形窗口**（协议限制）。
- 方案：VM 开发 + 编译验证 → Mac `cargo run` 看效果；或 VM 无头渲染（Xvfb + lavapipe）截图验证。
- wgpu / winit 跨平台，代码无需改动即可在 Mac 运行（macOS 走 Metal，支持最佳）。

## 5. 下一步

- M1 第 2 步：**三角形 + shader**（渲染管线，理解 GPU 怎么画画）。
- M1 后续：方块 + 移动 + 相机（达成后 = M1 能动）。
- 阶段二：三人各自小游戏（评估理解度），范围相当便于互评。
- M3 前：评估 bevy_ecs 底料；立 ADR-0002。
- 可并行：验收闭环 + 观察通道设计。

## 6. 外部架构提案分析（2026-08-19）

> 来源：豆包对话《标准化可复用资产池》提案（7 层架构：标准组件库 / 玩法模块 / 语义资产库 / 品类模板 / AI 智能匹配 / 落地保障 / 路线融合）。
> 性质：架构上正确，但时机上对 3 人无经验团队危险——是 5 年后的终局图景，不是第 1 个月的施工图。

### 提案的核心主张

把引擎设计成「一切皆可复用的标准化资产池」，AI 做智能匹配→组装→微调，人只管创意和调优。做过的项目自动沉淀回资产池，越做越快（飞轮效应）。

### 判断：方向对，时机错

**与 ADR-0002 的关系**：提案的终局图景（标准组件库 + 可插拔系统 + 品类模板 + AI 自动沉淀）本身不违背 ADR-0002 的「游戏驱动」原则——但提案暗示**现在就建那套基础设施**，这直接违背了「不为想象中的场景预付复杂度」。

| 提案层 | 判断 | 时机 |
|---|---|---|
| 标准组件库（20+ 个） | 偷：先让游戏自然长出 10+ 张卡，再标准化 | M3 后 |
| 可插拔系统库 | 已有（玩具 ECS），换 bevy_ecs 时正式化 | ADR-0003 |
| Archetype 实体模板 | 偷：setup_scene 重构成模板，成本低收益高 | 现在 |
| 玩法模块库 | 推到第 2 个游戏做完后提炼 | M4+ |
| 语义资产库 | 推到有美术资产需要管理时 | M5+ |
| 品类模板 | 推到做完 2 个同类型游戏后 | 远期 |
| 包管理/版本控制 | 推到 50+ 张能力卡时 | 远期 |
| AI 自动沉淀 | **永远用人决策**：人决定什么提炼，AI 照卡执行 | — |

### 多智能体路线判断

提案里 AI 干三件事（匹配/适配/沉淀）可拆成三个专精 agent，但**现在不该走多智能体路线**：6 张卡的数据量、3 人团队的协调成本、以及「人+AI」多角色模式已够用。多智能体在「单 AI 上下文装不下所有能力卡、引擎分 3 层以上」时再考虑。

### 结论

把提案的终局图贴在墙上当北极星可以，但**不现在建基础设施**。先做完游戏，让资产池自然长出来，然后提炼。这正是 ADR-0002 说的「引擎是长出来的，不是建出来的」。
