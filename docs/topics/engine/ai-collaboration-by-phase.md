# 游戏全生命周期的人机分工——从立项到打磨

## 结论

一个环节能让 AI 接管多少，取决于那个环节的**验收句可数字化到什么程度**。开发阶段之所以最顺，是因为它恰好是验收句最好写的环节；同一原则推广到立项、需求、美术、试玩、构建，就得到全景分工表。人的不可替代区收敛为四个词：品味、好玩、止损、审美。

## 正文

### 全景分工表

| 环节 | 验收句可写吗 | 人守什么 | AI 干什么 |
|------|------------|---------|----------|
| 立项（做什么游戏） | ❌ 品味 + 价值判断 | 做什么、值不值得、何时止损 | 可行性标价、候选结构化对比、决策留痕（ADR） |
| 需求 | ⚠️ 公式可/好玩不可 | 「下一个做什么」的筛选 | 追问逼需求成形（验收句写不出=没想清楚）、推演边界数值、记录决策理由 |
| 开发 | ✅ 完全数字化 | 立卡、验收、review | 照卡实现（已验证的主场） |
| 美术 | ⚠️ 规格可/审美不可 | 风格方向、挑选、说清为什么 | 批量生成、规格化处理、技术接入、一致性检查（详见 [[topics/game-design/art-pipeline-human-ai-division|美术协作笔记]]） |
| 试玩/QA | ❌ 主观 | **必须人玩**，记录不爽点 | 观察通道（日志/截图/测试）承接结构化输入 |
| 构建/发布 | ✅ 完全客观 | 何时需要（demo 没被玩之前不做） | 全自动化，AI 主场 |
| 知识沉淀 | ✅ | 关键决策拍板 | 编译、索引、维护 |

### 立项：方法论 = 放大版的卡流程

| 卡流程 | 立项对应物 |
|--------|-----------|
| 验收句 | 成功标准（demo 给朋友试玩算成） |
| 设计变更字段 | ADR |
| 依赖字段 | 团队能力现状 |
| 一卡一提交 | 一个项目一个明确阶段 |

warlock 的路径（m1 学渲染 → m2 学 ECS 组合 → wave-survival 学完整闭环）是**学习驱动立项**的教科书案例：每个项目的立项问题是「下一步该学什么」而非「什么市场机会」。立项决策全部留痕（含「不做什么」的 ADR-0004 退役路线）。

### 需求：不是写出来的，是玩出来的

需求的四个真实来源：玩的时候不爽（人）、旧项目教训（记忆+记录）、GDD 既定设计（人写）、技术债（撞上才知道）。**没有一个需求是 AI 发明的**——AI 的角色是追问成形、推演边界、记录理由。

「点子池」模式：在 GDD 或 backlog 维护一个缓冲区，条目只记「来源 + 一句话」，**不要求写验收句**（那是立卡时的事）。把需求的模糊态和开发就绪态分开：点子不因没想清楚被丢掉，也不因记下来被迫马上想清楚。

```
玩 → 不爽 → 记入点子池（模糊态）→ 开工时捞出 → 能写出验收句 → 立卡（就绪态）
```

### 试玩：开发之外的下一个瓶颈

demo 能玩通整局 = 需求生产线点火。关键动作：试玩 20 分钟 → 记「不爽点」→ 转成新卡或调参项 → 回到卡流程。bevy_egui 调参面板是这个闭环的关键零件（玩着调、爽了记数值）——把主观手感实时翻译成客观参数，是「好玩」这种写不出验收句的东西进入卡流程的唯一通道。

### 构建与节奏

一条命令出可玩 build 给朋友，够了。Steam 页面/多平台/版本管理——demo 被玩过之前都是提前抽象，和提前建通用引擎是同一种浪费。
